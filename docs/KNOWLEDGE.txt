================================================================================
ОБХОД БЕЛЫХ СПИСКОВ (ru.whitelist.bypass) — БАЗА ЗНАНИЙ ДЛЯ НАСТРОЙКИ
Версия документа: 0.1.14
Формат: обычный текст, UTF-8. Рассчитан на чтение и человеком, и LLM, которой
поручают настройку приложения через файл настроек .json.

КАК ЧИТАТЬ ЭТОТ ФАЙЛ

  Раздел 0 — что вообще делает приложение и в каком порядке; 0.4 — порядок попыток
             при подключении, 0.5 — кнопки в уведомлении (в том числе пауза),
             0.6 — экран «Рабочие конфиги» (проверка и чистка пула руками),
             0.7 — интерфейс и дизайн-система, 0.8 — поддержка проекта (адреса).
  Раздел 1 — файлы данных и их форматы (пул, чёрный список, стратегии).
  Раздел 2 — каждая настройка: ключ, тип, допустимый диапазон, значение по
             умолчанию, что именно приложение с ней делает, на что влияет,
             какие крайности ломают работу.
  Раздел 3 — вычисляемые величины (что считается «рабочим»).
  Раздел 4 — наборы настроек.
  Раздел 5 — правила правки .json (в том числе LLM): что можно, чего нельзя.
  Раздел 6 — как по консоли понять причину проблемы.
  Раздел 7 — правила ядра Xray 26 по совместимости конфигов.

  Терминология:
    конфиг      — одна строка-ссылка vless://, trojan://, ss://, vmess://
    пул         — список конфигов с ИЗМЕРЕННОЙ скоростью (files/pool_wifi.txt
                  или files/pool_lte.txt — у каждой сети свой)
    пинг        — проверка TCP/TLS-доступности, НЕ рабочести
    замер       — реальная загрузка через поднятое ядро Xray, это и есть рабочесть
    дорожка     — один параллельный экземпляр ядра при замере
    линия       — локальный ciadpi (DPI-обход) между ядром и VPN-сервером

0.1. Из чего состоит приложение

  MainActivity          главный экран (OLED, без карточек): состояние, круглая
                        «Подключить», строка пула, линейка «Поиск/Пул/Рабочие/
                        DPI/Журнал»; консоль скрыта, открывается кнопкой
  BypassVpnService      Android VpnService: TUN → tun2socks (hev-socks5-tunnel) →
                        локальный Xray (SOCKS 127.0.0.1:10811) → VPN-сервер
  XrayEngine            сборка JSON-конфига ядра из ссылки, запуск/остановка,
                        проверка совместимости, короткие тексты ошибок
  Probe                 разовый замер: поднять ядро на свободном порту → дождаться
                        SOCKS → скачать файл → КБ/с → погасить
  ConfigTester          параллельный пинг (TCP или TLS-handshake)
  QuickSearch           «Быстрый поиск»: пинг порциями → сразу замер → до первого
                        рабочего
  Pool                  пул рабочих конфигов: ДВА файла — files/pool_wifi.txt
                        и files/pool_lte.txt; без явной сети методы работают
                        с текущей сетью (Net.key)
  Blacklist             чёрный список нерабочих (SharedPreferences bypass_blacklist)
  Net                   тип сети: wifi | lte (неизвестное считается lte); по нему
                        выбираются пул, стратегия DPI и отметка сборки
  PoolIo                импорт/экспорт пула (.txt) с указанием пула (сеть)
  PoolPanel             содержимое «Рабочих конфигов» как блок: живёт и на первой
                        вкладке настроек, и на отдельном экране
  VpnStart              единая точка запуска: обычный VPN, конкретный конфиг, «только DPI»
  ConfigRepository      источники списков: скачивание, хранилище, дедупликация,
                        ленивая подгрузка по одному источнику
  DpiStrategies         стратегии ciadpi: список, обновление, автоподбор,
                        рабочие стратегии
  DesyncLine            локальная линия ciadpi для замеров (вне сервиса)
  DpiArgs               подстановка {sni}/{port} в аргументы ciadpi
  TorEngine/TorTunnel   Tor с мостами: резервный канал и загрузка списков
  TorCheck              проверка мостов по одному с замером
  NetChecker            TCP-пинг, TLS-пинг, проверка «есть ли интернет»
  Prefs                 все настройки, ключи и значения по умолчанию
  Presets               наборы настроек (готовые и импортированные)
  SettingsIo            экспорт/импорт настроек .json, консоль .json
  Help                  справка «ⓘ» по каждому пункту настроек
  BrowserActivity       встроенный браузер, только через Tor с мостами

0.2. «Собрать пул» — полный конвейер

  1) источники: скачать все sources; ошибка любого источника не обрывает сбор
  2) чёрный список вычитается из СКАЧАННОГО (ConfigRepository.dropBlacklisted):
     с 0.1.15 — только пересечение обоих списков (Blacklist.keysBoth): файл списков
     один на Wi-Fi и мобильный, и конфиг, мёртвый лишь у оператора, дома может
     работать. Остальное отсекается на сборке пула — Blacklist.filter(net):
     записи из Blacklist удаляются из configs.txt, чтобы не возвращаться с каждым
     обновлением списков; отдельно те же конфиги отсекаются из набора в памяти
  3) совместимость с ядром: XrayEngine.compatProblem отбрасывает то, что ядро
     не поднимет никогда (транспорт, flow, reality без pbk, VLESS/Trojan без TLS —
     кроме случая, когда включён allow_no_tls)
  4) обновление стратегий DPI (лениво, ошибка не критична)
  5) порядок обхода списков ПЕРЕМЕШИВАЕТСЯ (Collections.shuffle)
  6) ПАКЕТЫ по 200 конфигов (POOL_BATCH), пока не кончатся все списки:
     а) пинг пакета: ConfigTester, потоки ping_threads;
     б) скорость: дорожки speed_lanes, порог min_speed_kbit;
        свежие замеры пула (моложе 12 ч) переиспользуются;
     в) DPI-добор: бюджет 8 попыток на весь сбор, по очереди через ciadpi;
     г) прогресс сохраняется в пул после КАЖДОГО пакета (остановка не теряет
        найденное). Пул больше не заменяется «с нуля»: старые рабочие записи
        остаются, новые добавляются
  7) отчёт причин отказов пишется в консоль

  Почему пакетами: раньше один проход смотрел не больше 150 конфигов и
  останавливался на 25 рабочих — в пул попадали первые строки первого источника,
  а остальные списки не проверялись вовсе.

0.3. «Быстрый поиск» — порядок

  1) проверка сети по ping_targets
  2) из кандидатов выкидываются конфиги, уже лежащие в пуле, и чёрный список
  3) партия до 150 конфигов, пинг ПОРЦИЯМИ по 25
  4) как только в порции есть живые — они сортируются по пингу и меряются
     по одному (до первого рабочего, лимит 25 проверок за круг)
  5) если рабочего нет — следующая порция; не проверенные живые переносятся
     в следующий круг
  6) когда локальный список кончился — источники подгружаются по одному,
     затем лучшие из пула, затем (одна попытка) Tor

0.4. «Подключить» — порядок попыток (с 0.1.9)

  Подключение повторяет то, как конфиг попал в пул:

    а) конфиг замерен НАПРЯМУЮ (в pool_wifi/pool_lte 4 поля):
       1) попытка напрямую;
       2) если не вышло и включён desync_line — ОДНА попытка через линию ciadpi
          (стратегия — dpi_strategy для LTE / dpi_strategy_wifi для Wi-Fi);
       3) не вышло ни так, ни так → конфиг удаляется из пула (Pool.remove)
          и ставится в чёрный список на 7 дней.

    б) конфиг замерен ЧЕРЕЗ ОБХОД (в pool_wifi/pool_lte 5 полей, есть стратегия):
       1) попытка ровно с той стратегией, что дала канал при замере;
       2) если не вышло — одна попытка напрямую;
       3) иначе — то же самое: из пула в чёрный список.

  Успешное подключение перезаписывает запись пула: если поднялось через обход,
  стратегия сохраняется (чтобы следующее подключение шло так же), если напрямую —
  поле стратегии очищается.

  Исключение: конфиг, который ядро не примет при текущих настройках
  (XrayEngine.compatProblem: нет TLS, а allow_no_tls выключен), из пула убирается,
  но в чёрный список НЕ пишется — это ограничение настроек, а не мёртвый сервер.

  Монитор (auto_switch): если канал перестал отвечать и удалось переключиться на
  другой конфиг, прежний уходит из пула и в чёрный список. Если не поднялся никто —
  виновата сеть, и тогда не трогается никто.

  ПОРОГ И «204 БЕЗ ТЕЛА» (0.1.15). Probe.measureConfig возвращает ok только когда
  есть измеренная скорость. Ответ 204/пустой ответ означает «связность есть,
  скорость не измерена» — это ПРОВАЛ с hard=true: конфиг не попадает в пул и идёт
  в чёрный список, а BypassVpnService.activate такой конфиг не подключает.
  Раньше такой результат засчитывался успехом с фиктивной скоростью min_speed —
  и в пуле жили «VPN, которые только отвечают на проверку».

0.5. Кнопки в уведомлении (с 0.1.9)

  «Пауза» — снимает TUN и tun2socks: трафик идёт с хоста напрямую, как будто VPN нет.
    Ядро Xray при этом НЕ гасится, монитор останавливается (иначе он принял бы
    отсутствие канала за сбой и начал менять конфиги), wake-lock снимается.
    Пока пауза активна, кнопка в уведомлении — «Продолжить».
  «Продолжить» — снова поднимает TUN на том же конфиге, без нового перебора и без
    повторного замера скорости. Если локальный SOCKS ядра уже не отвечает (система
    придушила процесс), запускается обычное подключение с нуля.
  «Остановить» — полное выключение сервиса (как и раньше).
  «Переключить» — сменить конфиг, не отключая туннель; на паузе не работает.
    С 0.1.14 переключение идёт по ВСЕМУ пулу, а не по первым трём: старт — со
    следующего за текущим, до трёх попыток за нажатие (MAX_SWITCH_TRIES), курсор
    switchCursor запоминается, поэтому следующее нажатие продолжает дальше, а
    после конца пула идёт сначала. Не поднявшиеся уходят в чёрный список.
    В режиме Tor «Переключить» возвращает на обычный конфиг, если он есть.

  Состояния, которые видит экран: off | connecting | on | paused | error.

0.6. Рабочие конфиги и режим «только DPI» (0.1.13)

  Где это теперь: ПЕРВАЯ вкладка настроек «Рабочие»; отдельный экран PoolActivity
  остался для перехода с главного (кнопка «Рабочие»). Содержимое одно и то же —
  класс PoolPanel, а не две копии разметки.

  Два пула. Пул ведётся отдельно для Wi-Fi (files/pool_wifi.txt) и для мобильного
  интернета (files/pool_lte.txt): у оператора и дома разные блокировки, и «собранный
  в метро» список дома только мешает. Переключатель сверху меняет открытый пул;
  для ПОДКЛЮЧЕНИЯ всегда берётся пул текущей сети (Net.key). Пул, собранный не в той
  сети, помечается подписью «Открыт пул …, телефон сейчас в сети …».

  Что показывает: записи открытого пула по скорости — «<N>. <КБ/с> · пинг · замер N ч
  назад [· обход: <стратегия>]», ниже схема, host:port, имя. Первые 60 строк.

  Действия над одной строкой:
    «Подключить этот конфиг» — VpnStart.connectRaw: ровно этот конфиг, без перебора
                   пула и без резерва Tor. Порядок попыток тот же, что в 0.4.
    «Пинг»       — ConfigTester для одного конфига: только доступность сервера.
    «Перемерить» — Probe.measureConfig с той же стратегией, что записана у конфига;
                   иначе напрямую, а при неудаче — одна попытка со стратегией сети.
    «Убрать»     — Pool.remove из пула этой сети, без чёрного списка.
    «В ЧС»       — Pool.remove + Blacklist.add в список ТЕКУЩЕЙ сети (7 дней):
                   у экрана «Рабочие» своя сеть (переключатель Wi-Fi/мобильный),
                   и приговор действует ровно для неё.

  Массовые действия: «Пропинговать все», «Перемерить скорость у всех» (с
  подтверждением), «Обновить список», внизу «В чёрный список нерабочие (N) · <сеть>».

  С 0.1.14 после ЛЮБОЙ массовой проверки провалившиеся конфиги удаляются из пула
  автоматически (Pool.remove) и на 7 дней попадают в чёрный список — отдельную
  кнопку нажимать не нужно. Защита: перед удалением пингуются цели ping_targets;
  если не ответила ни одна, виновата сеть и не удаляется никто.

  Конфиги из буфера обмена и из файла. Кнопка «Вставить из буфера» берёт текст из
  ClipboardManager и передаёт его в PoolIo.importText(c, net, text, log) — тем же
  путём, что импорт файла: дедупликация (внутри текста и против пула), пинг,
  замер скорости, в пул попадает только прошедшее порог min_speed_kbit. Импорт
  всегда пишет в ОТКРЫТЫЙ пул, поэтому вставлять конфиги, снятые на Wi-Fi, нужно
  на вкладке Wi-Fi.

  Режим «только DPI» (вкладка «Только DPI», с 0.1.13). Обход без VPN-сервера:
  DesyncLine поднимает локальный ciadpi со стратегией dpi_only_strategy, сервис
  проверяет адреса из dpi_only_urls через его SOCKS, и только если хоть один
  открылся — создаёт TUN (establishTun(TorTunnel.DNS)) и ведёт трафик в ciadpi.
  Чужого сервера в цепочке нет, подписка VPN не расходуется. Монитор и
  «Переключить» в этом режиме не работают: переключать нечего. Состояние на главном
  экране — «Только DPI» (синяя метка, mode=dpi).
  Если не открылся ни один адрес — режим не включается и пишет ошибку: иначе
  телефон показывал бы «подключено», а YouTube оставался закрытым.

  Стратегии по сетям: dpi_strategy_wifi (Wi-Fi) и dpi_strategy (мобильный), обе
  правятся на вкладке «Обход»; пустое поле = встроенная для этой сети.

0.7. Интерфейс и дизайн-система (с 0.1.11)

  Все экраны собираются из одного набора решений — класс Ui (src/ru/whitelist/bypass/Ui.java).
  Раньше каждый экран строил вьюхи сам, и одинаковые вещи выглядели по-разному.

  ТОКЕНЫ
    Цвета (роли):        BG_OLED #000000 — фон ТОЛЬКО главного экрана (OLED: пиксели не
                         светятся, экономится заряд; текста там мало — крупная кнопка и
                         короткие подписи). На экранах со списками и полями ввода остаётся
                         BG #0B0F14: чистый чёрный под длинным белым текстом утомляет.
                         BG #0B0F14 — фон; SURFACE #131A24 — карточка; SURFACE_2 #1B2532 —
                         блок внутри карточки; STROKE #243040 — граница;
                         ACCENT #3DDC84 — «работает»/главное действие; ACCENT_INK #04210F —
                         текст на акценте; TEXT #E9F0F7; TEXT_DIM #93A6BA;
                         DANGER #FF6B6B; WARN #FFB020; INFO #64B5F6 (пауза); TOR #B388FF.
    Отступы (шкала 4dp): S1=4, S2=8, S3=12, S4=16, S5=24, S6=32. Других отступов в коде нет.
    Радиусы:             R_SM=10, R_MD=16, R_LG=20, R_PILL — «таблетки»/чипы.
    Шрифты:              h1 24sp bold; h2 16sp medium; body 14sp; caption 12sp dim;
                         overline 11sp + letterSpacing 0.12 (заголовки секций);
                         mono — адреса, ключи, журнал.
    Нажатие:             не меньше 48dp у обычных кнопок, 40dp у кнопок в строках списка.

  КОМПОНЕНТЫ
    Ui.card(ctx)            — поверхность: заливка SURFACE, граница 1dp, радиус 20, padding 16
    Ui.inner(ctx)           — вложенный блок (SURFACE_2, радиус 16, padding 12)
    Ui.chip(ctx, …)         — «таблетка» состояния/вкладки; paintChip() перекрашивает
    Ui.tab(ctx, …)          — чип-вкладка настроек (активная — залита акцентом)
    Ui.primary/secondary/ghost/danger/small — кнопки: главная, обычная, тихая, опасная, строка
    Ui.iconButton(ctx, "⚙") — квадрат 44dp в шапке (настройки, «назад»)
    Ui.header(ctx, …)       — заголовок экрана + подпись + правый элемент

  ГЛАВНЫЙ ЭКРАН С 0.1.13 (OLED-редизайн)
    Фон чистый #000000, карточек на экране нет. Сверху — состояние (чип + имя
    конфига), ниже — большая круглая кнопка 176dp (единственный крупный элемент),
    под ней подсказка, строка про пул текущей сети (тап → «Рабочие»), затем ОДНА
    линейка мелких кнопок высотой 44dp: «Поиск», «Пул», «Рабочие», «DPI», «Журнал».
    Консоль скрыта (View.GONE), открывается кнопкой «Журнал» и раскрывается сама
    при состоянии error. С 0.1.14 прокрутки на главном НЕТ: корень — обычный
    LinearLayout (не ScrollView), консоль имеет вес 1 и занимает ровно остаток
    экрана, кнопка — 160dp. Функциональность прежняя: те же действия, те же тексты.
    Ui.divider/spacer/h1/h2/body/caption/overline/mono

  ЭКРАНЫ
    Главный: шапка (⚙) → карточка состояния (чип статуса, имя текущего конфига, круглая
    кнопка 168dp с цветом по состоянию, подсказка под ней) → карточка «Действия»
    (Быстрый поиск / Собрать пул + пояснение) → карточка «Рабочий пул» (открывает рабочие
    конфиги) → карточка «Журнал» (копирование) → подвал с версией.
    Состояния кнопки: off — зелёная «Подключить»; connecting — оранжевая «Отмена»;
    on — красная «Отключить»; paused — синяя; tor — фиолетовая; error — тёмно-красная.
    Настройки: шапка (← сохраняет и закрывает) → чипы-вкладки (Списки, Обход, Tor, Данные,
    Инфо) → карточки секций → главная кнопка «Сохранить настройки» на каждой странице.
    Рабочие конфиги: шапка (←) → сводка → карточка проверок → список карточек конфигов
    (пинг-чип, схема/host, замер и стратегия, статус, две строки кнопок) → опасная кнопка
    «В чёрный список все нерабочие».

  ПРАВИЛА (чтобы правки не разъехались снова)
    1. Никаких цветов и размеров «по месту»: только константы Ui и его фабрики.
    2. Карточка не темнее фона — иначе она «проваливается»; вложенный блок светлее карточки.
    3. Один визуальный акцент на экран (обычно — главная кнопка).
    4. Текст-объяснение идёт подписью (caption), а не мелким серым абзацем в поле.
    5. Кнопка-действие подписывается глаголом; пояснение — отдельной строкой под ней.

0.8. Поддержка проекта (адреса)

  Экран: Настройки → «Инфо» → секция «Поддержка». Три равнозначных способа. В карточке
  только название сети и адрес (моноширинным), ниже — кнопка «Скопировать адрес», у Bitcoin
  дополнительно «Открыть в кошельке» (URI bitcoin:). Сумм, «ориентиров» и курсов в интерфейсе
  нет: сколько переводить — решает пользователь.

    USDT (TON)    UQBYs3wqrpoUsGoU2edVR7z6_1ctSH4HU2ZZf5DXPToQ3wgi
    USDT (TRON)   TUZeuyvA9dALj1ee78NSMXvnJeEXxYwZ1a
    Bitcoin       bc1qat0txl9ttmsz2le58yvfw9zvhg7pncj9mmr49h

  Правила, которые нельзя менять при правках текста:
    - сеть указывается рядом с каждым адресом (USDT в TON и USDT в TRON — разные сети);
    - никаких сумм и «ориентиров»: в карточке только сеть и адрес;
    - адрес показывается целиком и копируется кнопкой, вручную не набирается;
    - ничего не обещается взамен: ни подписки, ни приоритета, ни упоминаний в интерфейсе;

1. ФАЙЛЫ ДАННЫХ (не настройки; в .json настроек не попадают)

1.1. files/pool_wifi.txt и files/pool_lte.txt — пул
  (до 0.1.13 был один files/pool.txt; при первом запуске он переносится в
  pool_lte.txt, а pool_wifi.txt создаётся пустым — старые замеры делались в
  мобильной сети, и приписывать их Wi-Fi было бы враньём.)

  Формат строки (TAB — символ табуляции, поля через \t):
    4 поля: <кбит-в-секунду? нет: КБ/с> \t <пинг, мс> \t <время замера, мс epoch> \t <ссылка>
    5 полей: <КБ/с> \t <пинг> \t <время> \t <стратегия ciadpi> \t <ссылка>

  Пояснения:
    - первое поле — скорость в КБ/с (килобайтах в секунду), целое, > 0;
    - второе — пинг в мс или -1, если не измерялся;
    - третье — System.currentTimeMillis() момента замера;
    - пятое поле появляется ТОЛЬКО если конфиг заработал через DPI-обход;
      тогда при подключении берётся именно эта стратегия, а не dpi_strategy;
    - порядок в файле значения не имеет: при чтении пул сортируется по скорости
      по убыванию, при равной скорости — по меньшему пингу;
    - максимум 200 записей (лишние отбрасываются при сохранении);
    - с 0.1.14 «Собрать пул» сохраняет пул ПОСЛЕ КАЖДОГО ПАКЕТА и не выбрасывает
      прежние рабочие записи: они обновляются, если конфиг снова прошёл замер;
      одиночные записи добавляются
      через Pool.remember (успешное подключение, быстрый поиск);
    - запись удаляется, если конфиг перестал подключаться (ни напрямую, ни через
      обход) или если строка пула разобралась в мусор: держать в рабочих то, что
      не поднимается, бессмысленно — оно занимает попытку у каждого подключения.
      Удаление не обновляет отметку «пул собран».

1.2. bypass_blacklist (SharedPreferences: entries_wifi и entries_lte)

  С 0.1.15 список разделён по типу сети, как и пул: у оператора и домашнего Wi-Fi
  разные блокировки, и конфиг, не поднявшийся в мобильной сети, дома часто работает.
    entries_wifi — нерабочие в Wi-Fi;
    entries_lte  — нерабочие в мобильном интернете.
  Старый общий ключ entries при первом обращении переносится в entries_lte
  (прежние проверки шли в основном через мобильный интернет), флаг migrated_net_v1.
  Текущую сеть определяет Net.key(): Wi-Fi/Ethernet → wifi, остальное → lte.

  Формат: строки "<время epoch, мс>\t<канонический ключ конфига>".
  Канонический ключ — ConfigRepository.canonicalKey(ссылка): нормализованная
  ссылка без фрагмента (#имя), по ней и сравниваются конфиги.

  Правила:
    - попадают только «жёсткие» отказы: ядро не поднялось, SOCKS не открылся,
      нет данных (таймаут), «связность есть, скорость не измерена» (ответ 204 без
      тела — с 0.1.15 это провал, а не успех), а также конфиг из пула, который не
      поднялся ни напрямую, ни через обход (он одновременно удаляется из пула).
      «Ниже порога» НЕ попадает — такой конфиг рабочий, просто медленный;
    - запись живёт 7 дней (Blacklist.TTL_MS), потом игнорируется;
    - успешный замер или успешное подключение снимают запись;
    - чистка вручную: настройки → «Данные» → «Очистить список нерабочих» —
      чистит ОБА списка (Blacklist.clearAll);
    - влияет на сбор пула, быстрый поиск, импорт .txt и подключение — всегда в
      пределах текущей сети (Blacklist.add/forget/filter/size по Net.key).

1.3. files/strategies.txt — скачанные стратегии DPI

  По одной стратегии в строке; комментарии и мусор отбрасываются при обновлении.
  Максимум 60 (MAX_STRATEGIES). Встроенный минимум (DpiStrategies.BUILT_IN)
  существует всегда, даже если файла нет.

1.4. bypass_dpi_working (SharedPreferences, ключ list) — рабочие стратегии

  До 8 строк, свежие первыми. Пополняется, когда конфиг прошёл замер через
  DPI-обход или когда подключение с обходом удалось. Автоподбор пробует эти
  стратегии ПЕРВЫМИ, до скачанного списка. Сбрасывается кнопкой «Забыть рабочие
  стратегии» и не влияет на уже сохранённые связки в пуле.

1.5. files/strategies_rank, tor_report и прочее

  tor_report        — текст последнего отчёта «Проверить мосты и источники».
  tor_bridge_rank   — порядок мостов, отсортированный по результатам проверки;
                      при подключении Tor пробует мосты в этом порядке.

1.6. Консоль (лог) и её .json

  SettingsIo.consoleJson пишет: app, kind, format, version, savedAt, lines[],
  text, pool (число конфигов). Паролей и ключей конфигов в консоли НЕТ.

KEY: min_speed_kbit                     тип: int     диапазон: 8..160000
по умолчанию: 32
  Порог «рабочего» конфига в КИЛОБИТАХ в секунду.
  Внутри: Prefs.minSpeedKbps() = round(min_speed_kbit / 8), то есть 32 → 4 КБ/с.
  Где применяется: после замера (Probe.measureSpeed) и в сборе пула — конфиг
  попадает в пул, только если его КБ/с >= minSpeedKbps. В быстром поиске тот же
  критерий для «найден рабочий».
  Влияние: слишком высокий порог → пул пустой, поиск «ничего не нашёл» при живых
  серверах (частая ошибка на мобильном интернете). Слишком низкий → в пул
  попадает мусор, подключение «есть, но ничего не грузится».
  Практика: мобильный интернет 32–128; Wi-Fi 512–1024.
  Замечание: конфиг ниже порога НЕ отправляется в чёрный список.

KEY: speed_lanes                         тип: int     диапазон: 1..8
по умолчанию: 6 на восьмиядерном телефоне (Prefs.defaultSpeedLanes = ядра-2, 2..6)
  Сколько экземпляров ядра мерить скорость одновременно. Каждая дорожка —
  отдельный Xray на своём локальном порту (Probe.freePort).
  Значение рассчитано на целевые SoC уровня Snapdragon 865, Snapdragon 7 Gen 3,
  Snapdragon 6 Gen 4, Dimensity 7350 — у всех 8 ядер.
  Влияние: 6 дают почти линейное ускорение перебора и укладываются в память
  (каждый Xray — десятки МБ); 8 — потолок, дальше упираемся в канал и в память;
  1 — самый точный замер (вся полоса одному конфигу) и самый долгий.
  Миграция 0.1.14: у кого осталось старое значение по умолчанию (4), оно заменяется
  на новое; свои значения не трогаются (флаг migrated_speed_v3).

KEY: target_region                      тип: строка  значения: eu | asia | us
по умолчанию: eu
  Целевой регион проверок (Regions, главный экран — чипы под линейкой кнопок,
  настройки — «Списки» → «Целевой регион»). Регион задаёт ДВА адреса: цель пинга
  и ссылку замера. Prefs.setRegion() записывает регион и подставляет его сайты в
  ping_targets/speed_urls/health_urls (свои правки после этого не трогаются, пока
  регион не сменят снова).
    eu   пинг raw.githubusercontent.com:443, скорость — ping_tested.txt (GitHub)
    us   пинг raw.githubusercontent.com:443, скорость — vless.txt (GitHub)
    asia пинг www.lenovo.co.jp:443,        скорость — https://www.lenovo.co.jp/
  Почему так: GitHub отдаётся краем Fastly (есть европейские и американские узлы),
  его файл нельзя «точечно разрешить» под один сервис; в Азии GitHub медленнее и
  хуже достижим, поэтому там региональный сайт Lenovo (не в белых списках,
  отдаётся локальным краем CDN).
  Миграция 0.1.15 (migrated_region_v1): старые дефолтные наборы (5 целей пинга,
  4 ссылки) заменяются сайтами региона; правленые вручную значения не трогаются.

KEY: speed_urls                          тип: список строк (по одной в строке)
по умолчанию (0.1.15): ОДНА ссылка — Regions.speedUrl(регион)
  eu   raw.githubusercontent.com/luxxuria/harvester/ping_tested.txt
  us   raw.githubusercontent.com/kort0881/.../ru-sni-local/vless.txt
  asia https://www.lenovo.co.jp/
  Что скачивается через туннель для замера. Пробуются по очереди до первого
  успешного; дополнительные строки можно вписать руками.
  Почему одна: набор из четырёх маскировал проблему — «работает» могло означать
  «сработал один из четырёх», а скорость мерилась по другому хосту, чем пинг.
  ВАЖНО: первыми идут адреса, которые нельзя «точечно разрешить». Появилась масса
  конфигов, открывающих только Discord/YouTube и пару CDN, — если мерить по ним,
  такой конфиг выглядит рабочим, а остальной интернет через него не открывается.
  Ответы generate_204 стоят в конце: тела в них нет, скорость по ним не считается.
  Требования: маленький размер, без авторизации, разные хосты/сети.
  Влияние: мегабайтные файлы превращают замер сотен конфигов в часы.

KEY: gate_timeout_ms                     тип: int     диапазон: 800..20000
по умолчанию: 3000
  Окно замера на один URL, мс. Отсчитывается от ПЕРВОГО полученного байта;
  на соединение и TLS отдельный запас сверху, поэтому 1500 мс не превращаются
  в «нет данных» на медленном старте.
  Влияние: < 800 → много ложных «нет данных»; > 10000 → сбор пула растягивается.

2.2. ПОИСК И ПИНГ
--------------------------------------------------------------------------------

KEY: ping_threads                        тип: int     диапазон: 1..256
по умолчанию: 192 на восьмиядерном телефоне (Prefs.defaultPingThreads = ядра*24, 32..256)
  Параллельных проверок пинга. Пинг — только доступность порта: TCP-коннект,
  а для TLS-конфигов сначала TLS-handshake, при неудаче — обычный TCP.
  Пинг висит на ожидании ответа и почти не грузит CPU, поэтому 24 сокета на ядро
  безопасны: 2000 конфигов проверяются за считанные секунды.
  Влияние: 256 — потолок (дескрипторы и память); < 20 — пинг 2000 конфигов
  занимает минуты. Миграция: старое значение по умолчанию (60) заменяется новым.

KEY: ping_timeout_ms                     тип: int     диапазон: 300..15000
по умолчанию: 2000
  Таймаут одного пинга. Влияние: < 700 → на плохой сети «умирают» живые;
  > 5000 → сбор растягивается, а мёртвые всё равно видны за секунды.

KEY: ping_targets                        тип: список host:port
по умолчанию (0.1.15): ОДНА цель — Regions.pingTarget(регион):
  eu/us raw.githubusercontent.com:443, asia www.lenovo.co.jp:443
  Проверка «есть ли вообще интернет» в начале поиска/сбора. Если цель не
  ответила — в лог пишется предупреждение, но работа продолжается.
  Можно вписать несколько строк: проверяются параллельно, достаточно одной.
  Discord и YouTube из списка убраны: конфигов, которые открывают только их,
  слишком много, и по ним нельзя судить о доступности остального интернета.

KEY: health_urls                         тип: список URL
по умолчанию (0.1.15): ОДИН адрес — Regions.healthUrl(регион), тот же сайт,
                       по которому меряется скорость
  Проверка канала ЧЕРЕЗ туннель монитором. Если за switch_timeout_sec ни один
  не открылся — канал считается мёртвым, и при auto_switch конфиг меняется.
  Достаточно одного ответа, поэтому список остаётся мягким; «настоящий»
  зарубежный адрес стоит здесь первым, чтобы видеть, что открывается не только
  разрешённое. Discord и YouTube из проверки убраны (см. speed_urls).
  Влияние: тяжёлые страницы замедляют проверку и жгут трафик.

KEY: desync_line                         тип: bool    по умолчанию: true
  Пропускать линию до VPN-сервера через локальный ciadpi.
  Когда включено:
    - при подключении: сначала прямое соединение, при неудаче — через линию;
    - в сборе пула: до 8 непрошедших конфигов пробуются через линию, и при удаче
      в пул пишется пара «конфиг + стратегия»;
    - автоподбор (dpi_autotune) работает только при включённом обходе.
  Выключено → только прямые подключения; на живых блокировках половина
  конфигов «не работает».

KEY: dpi_strategy                        тип: string
по умолчанию: комплексная фрагментация (-o1 -s1+s -s3+s ... -a1 -An)
  Аргументы ciadpi. Поддерживаются короткий и длинный форматы; плейсхолдеры
  {sni} и {port} подставляются DpiArgs.build. Разбор — по пробелам.
  Приоритет источников стратегии при подключении:
    1) стратегия, сохранённая у конфига в пуле (пятое поле pool_wifi/pool_lte);
    2) это поле.
  Влияние: стратегии для zapret/nfqws (PROTO|ARGS) не работают — другой синтаксис.
  ВАЖНО (с 0.1.9): если конфиг в пуле замерен со своей стратегией, при подключении
  берётся она, а не это поле; автоподбор в таком случае не запускается.

KEY: dpi_sources                         тип: список URL, по умолчанию два репозитория
  Откуда скачивать списки стратегий. Обновление — кнопкой или в начале сбора пула.
  Встроенный минимум остаётся всегда.

KEY: dpi_autotune                        тип: bool    по умолчанию: true
  Подбирать стратегию при подключении: по очереди поднимать ciadpi и проверять
  доступность адресов из dpi_test_urls; первая подошедшая пишется в dpi_strategy.
  Порядок перебора: рабочие стратегии (bypass_dpi_working) → скачанный список.
  Стоимость: до ~30 секунд один раз за подключение.
  Выключено → используется ровно dpi_strategy.

KEY: dpi_test_urls                       тип: список URL
по умолчанию (0.1.10): raw.githubusercontent.com/luxxuria/harvester/ping_tested.txt,
                       www.instagram.com, x.com
  Адреса, по которым проверяется, «пробила» ли стратегия блокировку.
  Стратегия считается рабочей, если открылся хотя бы один адрес.
  Discord и YouTube убраны намеренно: стратегия, которая «пробивает» только их,
  дальше даёт канал, работающий для двух сервисов, — это и была жалоба «конфиг
  рабочий, а сайты не открываются». GitHub raw режется по SNI и точечно не
  разрешается, поэтому по нему видно настоящий обход.

KEY: allow_no_tls                        тип: bool    по умолчанию: false
  Разрешать конфиги без TLS (VLESS/Trojan без security=tls|reality).
  Причина: ядро Xray 26 (infra/conf, requiresTransportSecurity) отказывается
  поднимать такие outbound'ы к публичному адресу — разрешены только приватные
  IP и локальные домены. Под правило попадает больше половины публичных списков.
  Когда включено: приложение строит локальный ретранслятор — inbound
  dokodemo-door на 127.0.0.1, а outbound смотрит на loopback; relay-in
  маршрутизируется в outbound desync (ciadpi), если включён обход, иначе в direct.
  Когда выключено: такие конфиги отбрасываются ДО пинга, в консоли одна строка
  «Несовместимы с ядром: N (... — N)».
  Стоимость включения: один лишний локальный хоп на таких конфигах.

--------------------------------------------------------------------------------
2.5. СЕТЬ
--------------------------------------------------------------------------------

KEY: vpn_dns                             тип: string (через запятую/пробел/;)
по умолчанию: "1.1.1.1, 8.8.8.8, 9.9.9.9"
  DNS-серверы внутри ядра (блок dns), пробуются по порядку, дубликаты убираются.
  Пустое значение → подставляется значение по умолчанию.

KEY: ipv6                                тип: bool    по умолчанию: false
  Маршрутизировать IPv6 в туннеле. Включение имеет смысл, только если канал
  умеет IPv6; иначе приложения пробуют IPv6, ждут таймаут и «сайт не открывается».

KEY: auto_switch                         тип: bool    по умолчанию: true
  Переключать конфиг, если канал перестал отвечать (монитор: health_urls).
  С 0.1.9: конфиг, который перестал отвечать, после удачного переключения удаляется
  из пула и попадает в чёрный список. Если не поднялся ни один — не трогаем никого
  (виновата сеть, а не сервер).

KEY: monitor_interval_sec                тип: int     диапазон: 5..300
по умолчанию: 15
  Как часто монитор проверяет канал.

KEY: switch_timeout_sec                  тип: int     диапазон: 5..3600
по умолчанию: 15
  Сколько секунд без ответа считать потерей канала. < 5 → ложные переключения;
  > 60 → переключение приходит, когда пользователь уже ушёл.

KEY: boot_connect                        тип: bool    по умолчанию: false
  Подключаться после загрузки телефона (BootReceiver). Android может ограничить
  автозапуск — тогда нужно «Разрешить работу в фоне».

--------------------------------------------------------------------------------
2.6. TOR
--------------------------------------------------------------------------------

KEY: tor_fallback                        тип: bool    по умолчанию: true
  Если ни один VPN-конфиг не отвечает — пускать трафик через Tor-мосты.
  Медленно, без UDP. Без мостов Tor не поднимается вообще.
  На ручной режим НЕ влияет.

РЕЖИМ «TOR КАК VPN» (с 0.1.14, без отдельного ключа)
  Кнопка «Включить Tor-мост как VPN» на вкладке «Tor»: VpnStart.connectTor →
  ACTION_START + EXTRA_START_MODE=MODE_TOR. Сервис поднимает мосты сразу
  (bringUpTor(why, manual=true)), проверяет скорость через Tor по min_speed_kbit
  и только потом создаёт TUN. Переключатель tor_fallback не проверяется —
  человек попросил явно. «Переключить» из этого режима уводит на конфиг из пула.

KEY: tor_bridges                         тип: строка (мосты, по одному в строке)
по умолчанию: пусто → встроенные Vanilla из assets/fallback/tor_bridges_vanilla.txt
  Формат — строки obfs4/webtunnel/snowflake как есть, без префикса Bridge.

KEY: tor_bridge_wait_sec                 тип: int     диапазон: 5..120
по умолчанию: 10
  Лимит ожидания одного моста. Время проверки = мостов × лимит.
  > 30 смысла нет: это уже признак заблокированного моста.

KEY: tor_extra_torrc                     тип: строка (строки torrc как есть)
по умолчанию: пусто
  Дополнительный конфиг Tor. Синтаксическая ошибка → Tor не поднимется вовсе.

KEY: tor_report                          тип: string (служебное)
  Текст последнего отчёта проверки мостов. Правится только приложением.

KEY: tor_bridge_rank                     тип: string (служебное)
  Порядок мостов по результатам проверки. Правится только приложением.

2.7. ДАННЫЕ И СЛУЖЕБНЫЕ КЛЮЧИ
--------------------------------------------------------------------------------

KEY: embedded_enabled                    тип: bool    по умолчанию: true
  Использовать встроенный резерв конфигов (assets/fallback). Не скачивается,
  часть APK. Выключение → работа только со скачанными списками.

KEY: current_raw / current_name / current_host / current_port
  Текущий (последний подключённый) конфиг. Правится приложением; руками менять
  смысла нет, но при импорте .json они применяются.

KEY: pool_at                             тип: long (epoch, мс)
  Время последнего сохранения пула (устаревший общий ключ, читается как fallback).

KEY: pool_at_wifi / pool_at_lte          тип: long (epoch, мс)
  Время последней сборки пула КАЖДОЙ сети. Правится приложением.

KEY: dpi_strategy_wifi                   тип: string  по умолчанию: встроенная «для Wi-Fi»
  Стратегия ciadpi для Wi-Fi. Пусто = Presets.wifiStrategy(). У мобильного — dpi_strategy.

KEY: dpi_only_strategy                   тип: string  по умолчанию: встроенная «только DPI»
  Стратегия ciadpi для режима без VPN-сервера. Пусто = Presets.dpiOnlyStrategy().

KEY: dpi_only_urls                       тип: список строк
  Адреса, которыми режим «только DPI» проверяет, что обход действительно работает
  (по умолчанию youtube.com, discord.com, instagram.com). Не открылся ни один —
  режим не включается.

2.8. ЧЕГО В НАСТРОЙКАХ НЕТ
--------------------------------------------------------------------------------

  Пул, чёрный список, рабочие стратегии и скачанные списки — это ДАННЫЕ.
  Они не экспортируются в .json настроек, не импортируются из него и удаляются
  кнопкой «Удалить скачанные списки и пул» (пул и списки) или «Очистить список
  нерабочих конфигураций» (чёрный список).


================================================================================
3. ВЫЧИСЛЯЕМЫЕ ВЕЛИЧИНЫ
================================================================================

  3.1. minSpeedKbps   = max(1, round(min_speed_kbit / 8))       — порог в КБ/с
  3.2. «рабочий конфиг» = замер прошёл И КБ/с >= minSpeedKbps
  3.3. «живой» (после пинга) = latency >= 0; рабочесть НЕ означает
  3.4. «несовместимый» = compatProblem() != null — не пингуется и не меряется
  3.5. «в чёрном списке» = запись моложе 7 дней
  3.6. POOL_REUSE_MS = 12 ч — замеры пула моложе переиспользуются, не перемеряются
  3.7. POOL_BATCH = 200 конфигов за пакет; сбор идёт до конца списков (стопа
       «набралось N рабочих» больше нет)
  3.8. DPI_RETRIES = 8 конфигов за сбор пробуются через линию ciadpi
  3.9. QuickSearch: PING_BATCH = 150, PING_CHUNK = 25, PROBES_PER_ROUND = 25


================================================================================
4. НАБОРЫ НАСТРОЕК (Presets)
================================================================================

  «Стандарт»      значения по умолчанию: DPI-обход включён, автоподбор включён,
                  порог 32 кбит/с, 4 дорожки, ping 60/2000 мс, монитор 15/15 с
  «Wi-Fi»         без DPI-обхода и автоподбора, выше порог — быстрый замер
  «Белые списки»  низкий порог, только white-источники
  «Мой из .json»  создаётся автоматически при импорте настроек; хранится в
                  SharedPreferences и попадает в экспорт.

  Применение набора записывает значения в настройки и перезагружает экран.
  Готовые наборы удалить нельзя.


================================================================================
5. ПРАВИЛА ПРАВКИ .json (в том числе через LLM)
================================================================================

  5.1. Формат: {"app": "...", "kind": "settings", "format": 1, "version": "0.1.8",
       "savedAt": ..., "settings": { "<ключ>": <значение>, ... } }
  5.2. Применяются только ИЗВЕСТНЫЕ ключи и только с совпадающим типом:
       int-ключи должны быть числами, bool — true/false, строки — строками.
       Лишнее игнорируется; в сообщении видно, сколько применено и пропущено.
  5.3. Списки (sources, speed_urls, ping_targets, health_urls, dpi_sources,
       dpi_test_urls, tor_bridges) — ОДНА строка с переводами строк между
       элементами, а не JSON-массив.
  5.4. Значения вне диапазона не ошибка: приложение зажимает их в допустимый
       диапазон (Prefs.clamp). Поэтому «1000000» в ping_threads превратится в 256.
  5.5. Нельзя «включить» несуществующее: например, allow_no_tls влияет только
       на VLESS/Trojan без TLS, а не на transport-типы.
  5.6. После импорта настройки применяются сразу и сохраняются как набор.
  5.7. Чего делать не надо:
       - вписывать в tor_extra_torrc произвольный текст (Tor не поднимется);
       - ставить min_speed_kbit выше реальной скорости канала (пул останется пустым);
       - ставить ping_timeout_ms < 700 на мобильном интернете;
       - менять current_* руками в расчёте «переключить конфиг»: подключение
         берёт конфиг из пула, а не из этих ключей.


================================================================================
6. ДИАГНОСТИКА ПО КОНСОЛИ
================================================================================

  «Несовместимы с ядром: N (... — N)»
      Ещё до пинга отброшено то, что ядро не поднимет. Чаще всего — VLESS без TLS
      (см. allow_no_tls). Если таких много, включите allow_no_tls.

  «Чёрный список: N ... пропускаю»
      Конфиги, которые уже не работали, не проверяются (неделя).

  «Пинг: живых X из Y ... из них только TCP: Z»
      Z — TLS-handshake не прошёл, но TCP ответил. Это нормально для Reality.

  «ядро не запустилось: ...»
      Смотрите короткий текст: он переведён из длинной цепочки infra/conf.
      Частые: «не пускает без TLS», «REALITY работает только с raw/xhttp/grpc»,
      «ядро не знает такого транспорта».

  «нет данных (N URL): таймаут ответа»
      Ядро поднялось, но файл не скачался: сервер мёртв или блокирует.
      Такой конфиг уходит в чёрный список.

  «SOCKS не открылся за 4 с»
      Ядро не поднялось или порт занят. Проверьте число дорожек (speed_lanes).

  «Пул собран: N рабочих из M живых»
      Если N = 0 при M > 0: почти всегда слишком высокий min_speed_kbit,
      либо канал действительно не тянет (проверьте вручную).

  «Пустой пул» + «исследуйте allow_no_tls»: см. раздел 7.


================================================================================
7. СОВМЕСТИМОСТЬ КОНФИГОВ С ЯДРОМ XRAY 26
================================================================================

  7.1. Транспорты (network / type):
       поддерживаются: tcp (он же raw), ws/websocket, grpc, httpupgrade,
                       xhttp/splithttp
       УДАЛЕНЫ из ядра: h2, h3, http, quic  (их заменил xhttp)
       не строятся приложением: kcp, mkcp, hysteria, masque, xdrive

  7.2. Шифрование (security):
       none, tls, reality.  xtls из ядра убран.
       reality требует pbk (publicKey) и sni, и работает только с tcp/raw,
       xhttp/splithttp и grpc.

  7.3. flow: только xtls-rprx-vision, только на tcp/raw и только с TLS/REALITY.

  7.4. VLESS/Trojan без TLS к ПУБЛИЧНОМУ адресу ядро не поднимает вообще
       (infra/conf: requiresTransportSecurity). Исключения:
         - адрес — приватный/loopback/link-local IP или локальный домен;
         - у VLESS задано собственное шифрование (encryption=mlkem...);
         - включён allow_no_tls (тогда работает локальный ретранслятор).
       Это не баг приложения: правило самого ядра.

  7.5. vmess: транспорт и TLS берутся из base64-JSON ссылки, а не из query.

  7.6. Shadowsocks: методы aes-128-gcm, aes-256-gcm, chacha20-poly1305,
       xchacha20-poly1305 и семейство 2022-blake3-*; нужен пароль.

# Как в Throne устроен подбор конфигов — разбор по исходникам

Дата: 2026-11-06. Источник — репозиторий `throneproj/Throne` (≈8000 звёзд, ветка `dev`),
разобраны файлы:

| Слой | Файл |
|---|---|
| ядро, замер | `core/internal/probe/urltest.go`, `core/internal/probe/probe.go` |
| ядро, RPC | `core/internal/rpc/urltest.go`, `core/internal/testenv/testenv.go` |
| GUI, батчи | `src/engine/tests/TestRunner.cpp` (`kTestRunnerBatchSize = 100`) |
| GUI, экшены | `src/ui/mainWindow/mainwindow_setup.cpp` (`actionUrl_Test_Selected`, `actionUrl_Test_Group`) |
| GUI, дедуп | `src/ui/mainWindow/mainwindow_profiles.cpp` (`on_menu_delete_repeat_triggered`), `Configs::ProfileFilter::Uniq` |

Throne — это C++/Qt-оболочка и Go-ядро на форке sing-box; тот же `core` используют
мобильные сборки (`core/mobile/*`), так что архитектура замера у них общая.

---

## 0. Короткий ответ на «как у них сделано»

1. **Партия = один экземпляр ядра.** На каждые **100** профилей строится **одна** временная
   конфигурация sing-box, где каждый конфиг — это outbound с тегом (`proxy-N`), а не отдельный
   процесс и не отдельный локальный порт.
2. **Замер идёт внутри процесса**: проба берёт `adapter.Outbound` по тегу и делает
   `outbound.DialContext(...)` — HTTP-запрос «сквозь» конфиг без SOCKS-порта, без TUN и без
   второго ядра. Поэтому 100 параллельных проверок стоят почти ничего.
3. **Ограничитель — семафор на 100** (`MaxConcurrentTests = 100`, `normalizeConcurrency`).
4. **Один GET на конфиг** (плюс второй, «тёплый», для не-текущих), таймаут по умолчанию
   **3000 мс**, URL по умолчанию — `http://cp.cloudflare.com/` (google.com — это то, что вы
   вписали сами в настройку `test_url`).
5. **Никакой эвристики «группами по 10»** в Throne нет. Дедупликация есть, кэш результатов
   есть, «не судить конфиги, когда упала сеть» есть, а «соседние имена» — нет.

## 1. Загрузка сборника (до 5000 вариантов)

- Сборник = **группа** (`Configs::Group`) с полем `url`; обновление —
  `Subscription::updater()->RefreshGroup(...)`. Жёсткого лимита на размер группы нет: 5000
  строк парсятся целиком.
- Разбор форматов: `SubscriptionParser` (base64-подписки, v2rayN/v2rayNG, sing-box JSON),
  `clash.cpp` (Clash YAML), `vpnFileImport` (файлы), плюс deep-link.
- При обновлении работает **сверка** `Subscription::Reconcile` по отпечаткам
  (`ProfileKeys { content, identity }`): содержимое конфига и «личность сервера». Старые
  профили по отпечатку **переиспользуются** — им сохраняют `id`, а значит и результаты
  замеров, позицию в группе, закрепления.
- Практический потолок всё же есть, но не на загрузке, а на **отборе в боевой конфиг**:
  `autoSelector.kPoolCap = 3000` (пул, из которого выбирают) и `buildLimit` — по умолчанию
  **300**, максимум **500** членов попадает в конфиг.

## 2. Удаление дубликатов

- Явное действие меню: `on_menu_delete_repeat_triggered` → `Configs::ProfileFilter::Uniq`.
  Дубли в Throne **позиционные**: один `id` может стоять в группе несколько раз, и разные
  `id` могут описывать один и тот же конфиг (issue #1775).
- При обновлении подписки дубли режет `SubscriptionReconcile` по отпечатку `content`
  (нормализованный текст конфига) — «каждый старый профиль занимается максимум один раз,
  в порядке группы, идентичными приходами в порядке прихода».
- Важная деталь: `identity` (сервер) и `content` (полный конфиг) — **разные** ключи. Две
  строки с одним `host:port`, но разными UUID — это не дубликаты, а два разных выхода.

## 3. Тестирование: точная механика

### 3.1. GUI режет выборку на партии по 100

```cpp
constexpr int kTestRunnerBatchSize = 100;      // src/engine/tests/TestRunner.cpp
for (int i = 0; i < profileIDs.length(); i += kTestRunnerBatchSize) {
    auto profileIDsSlice = profileIDs.mid(i, kTestRunnerBatchSize);
    auto profiles = profilesRepo->GetProfileBatch(profileIDsSlice);
    runBatch(profiles, profileIDsSlice);        // одна RPC Test на партию
}
```
Партии идут **последовательно**; внутри партии — до 100 параллельных проб. Дедлайн RPC
считается как `раунды × таймаут + разброс спавна + запас`, потому что `Test` отвечает
только когда партия закончилась целиком.

Точки входа (меню): `actionUrl_Test_Selected` → выбранные профили,
`actionUrl_Test_Group` → **вся текущая группа** (`CurrentGroup()->Profiles()`), без выбора
действие применяется к группе (`get_selected_or_group`, режим `2`).

### 3.2. Ядро: семафор, две попытки, честный таймаут

```go
const MaxConcurrentTests = 100                 // core/internal/probe/probe.go
const URLTestTimeout    = 3 * time.Second      // core/internal/probe/urltest.go

func normalizeConcurrency(max int) int {
    if max <= 0 || max >= 500 { return MaxConcurrentTests }   // <=0 и >=500 → 100
    return max
}
```
`runBatch` заводит по горутине на тег, вход в пробу — через буферизованный канал-семафор на
`normalizeConcurrency`; между спавнами `time.Sleep(2ms)`, чтобы не залить планировщик.
Результаты собираются в map, потом выдаются **в порядке переданных тегов** (стабильно для
таблицы).

Затем на каждый тег:
1. `awaitTunnels` — ожидание рукопожатия для туннельных протоколов (OpenVPN/OpenConnect):
   до 10 с (`TunnelHandshakeTimeout`), а для «холодной» пробы первый запрос получает ещё
   `+5 с` (`TunnelStartupTimeout`) — иначе туннель, который ещё поднимается, выглядел бы мёртвым;
2. `http.Client` с транспортом, у которого `DialContext` идёт **прямо в outbound** (все
   установленные соединения записываются, чтобы закрыть их при возврате пробы);
3. `urlTest(...)`: GET, замер = время до заголовков ответа, тело дочитывается максимум
   `64 КиБ` и закрывается (иначе соединение не переиспользуется и следующая проба снова
   «холодная»);
4. флаг `twice`: у обычного замера **два** запроса — холодный и тёплый, в зачёт идёт второй
   (стабильнее и ближе к реальности). Для «проверить текущий» — один, потому что живой
   инстанс уже прогрет.

### 3.3. Отмена и поток результатов

Отмена — один общий контекст (`probe.TestContext()`, `CancelTests()` переармирует его).
Прерванный тег получает `ErrTestAborted` и **не публикуется и не сохраняется** — в коде это
написано прямо: «an aborted tag is not a measurement». Результаты по ходу делаются в
`URLReporter`, GUI их забирает поллингом `QueryURLTest` и обновляет строки вживую.

### 3.4. Что попадает в ячейку

`Profile::DisplayTestResult()`:
- `latency > 0` → `N ms` (+ страна флагом, скорость ↓↑ и внешний IP, если их мерили);
- `latency < 0` → `Unavailable`;
- `kLatencyConnectOnly` → `Connect OK` — туннель поднялся, но запрос не прошёл (это ставится
  для VPN-профилей, у которых ядро подтвердило соединение);
- `0` → пусто, «ещё не мерили».

### 3.5. Дефолты, которые вы видели

```cpp
QString test_latency_url = "http://cp.cloudflare.com/";   // настройка test_url
int     url_test_timeout_ms = 3000;                       // настройка test_timeout_ms
int     test_concurrent = 10;                             // настройка test_concurrency
```
То есть «100 за раз, 3000 мс» = `test_concurrency` выставлен в 100 (или ≥500, что ядро
нормализует в 100) и таймаут 3 с. Значение 100 — это ещё и **жёсткий потолок**: больше ста
одновременных проб Throne не запускает ни при каких настройках.

## 4. Порядок строк и «соседние группы»

- Порядок в группе — это **порядок прихода из подписки** (`GroupSortMethod::Raw`).
  Сортировки, доступные пользователю: `Raw`, `ByType`, `ByAddress`, `ByName`, `ByTestResult`,
  `ById`, `ByTraffic`, `BySecurity`, `ByLatency`.
- Ваше наблюдение («имена идут подряд, соседние — с одной сети») в Throne **не
  эксплуатируется**: тест идёт по списку сверху вниз партиями по 100 и не делает попыток
  «если один из десяти жив — проверить десяток целиком, иначе пропустить».
- Эвристика «а не виновата ли сеть» реализована **наоборот** — не по соседям, а отдельной
  прямой пробой: у автоселектора есть `connectivityURL` («direct probe used to spot a local
  outage»), и пока прямой пробник не отвечает, ядро ставит состояние `suspended`:
  «Core froze its ranking (local network down); nothing may be judged broken while this is set».
- Похожая логика «соседей» есть в двух других местах, и там она честная:
  - **сканер IP** (`ScanWorker`): идёт чанками `clamp(concurrency*4, 32, 2048)`, а неудачи
    **подтверждает** повтором (`confirmFailures`) — «unconfirmed, so nothing is removed; a
    pause re-runs the whole chunk». Плюс «family» = IPv4/IPv6: попадание по одному семейству
    ничего не доказывает про другое, и если семейство не ответило, **чанк переигрывается**,
    а не помечается мёртвым;
  - **редактор цепочки**: `runChainStepTest` тестирует каждый хоп «сам по себе и через
    хопы выше» (`ChainStepResult { hop, alone, latency, error }`), то есть сосед влияет на
    вердикт явно и видимо.

## 5. Автоселектор — вот это и есть «умный подбор»

`include/configs/outbounds/autoselector.h` (дефолты):

```cpp
kDefaultBuildLimit = 300    // максимум 500
kPoolCap           = 3000
kDefaultIntervalSec = 300   // перепроверка набора
kDefaultToleranceMs = 300   // «в пределах 300 мс — не хуже»
kDefaultExpected    = 3     // сколько держать подтверждённо живыми
kSuccessValiditySecs = 86400  // успех живёт 24 часа
kFailureValiditySecs = 3600   // провал — 1 час
kWatchIntervalSec   = 15      // «дежурный» опрос текущего выхода
kSampling = 10; kDialRetries = 2; kFailbackChecks = 3; kFailbackDelaySec = 60
```

Ранжирование (`AutoSelectorPlan.cpp`): по возрастанию задержки, но
- «не тестированный» (`latency == 0`) стоит **между** годным и «выше потолка»
  (`maxRTTms`) — чтобы свежая подписка исследовалась;
- провалившиеся — в конце;
- результаты с истёкшим TTL считаются отсутствующими, и тогда `needsRanking` → тестируются
  **только те, у кого нет свежего результата** (`tests_->runUrlTests(needed, ...)`).

Состояния члена: `ok | degraded | untested | dead | cooldown | suspect`; `suspect` — это
«пробы проходят, а реальные соединения в основном падают» (пассивная оценка по настоящему
трафику), отдельно от активных замеров.

| Ваш пункт | В Throne | Комментарий |
|---|---|---|
| 1. Загрузка сборника до 5000 | есть, без лимита на загрузку; в бой идёт 300–500 из пула 3000 | лимит — на отбор, не на импорт |
| 2. Удаление дубликатов | есть, явное действие + автосверка по отпечаткам при обновлении | `content` (конфиг) и `identity` (сервер) — разные ключи |
| 3. Группы по 10 + соседи | **нет** | вместо этого: партия 100 в одном ядре, семафор 100, TTL-кэш, прямой пробник сети |
| 4. URL google.com, 100 за раз, 3000 мс | ровно так и настраивается | URL и таймаут — настройки, 100 — потолок |
| 5. «Нажмите для проверки» — быстрый и точный результат | есть: тест выбранного/группы, два запроса (холодный+тёплый), ожидание рукопожатия туннеля | «Connect OK» — отдельный вердикт, когда туннель встал, а запрос не прошёл |

## 7. Чем это отличается от нас и что реально переносимо

У нас на Android **одно ядро на конфиг**: `Probe.measureConfig` поднимает отдельный
экземпляр Xray со своим SOCKS-портом. Поэтому «100 параллельно» у нас = 100 процессов ядра,
что на телефоне нереально; отсюда и наш быстрый TCP-отсев (`FastPing`) как первая ступень.

Ключевой приём Throne, который можно повторить и у нас без смены ядра, — **один Xray,
много inbound'ов**: в одной конфигурации Xray можно объявить N SOCKS-inbound'ов
(`in-N`) и N outbound'ов (`out-N`) и связать их правилами маршрутизации
`{ inboundTag: ["in-N"], outboundTag: "out-N" }`. Тогда проверка пачки конфигов — это N
параллельных HTTP-запросов по N локальным портам **одного** процесса, без TUN и без TUN-
подъёма, а не N процессов. Это прямой аналог `DialContext` в sing-box и главный вывод
исследования.

Что переносится независимо от ядра:
1. **Кэш результатов с TTL** (у нас 12 ч на пул; можно разделить «успех 24 ч / провал 1 ч»,
   как у них) — так 5000 строк не тестируются повторно.
2. **Два запроса: холодный + тёплый**, в зачёт второй — убирает ложные «медленно».
3. **Ожидание рукопожатия перед вердиктом** (у нас роль этого играет `waitSocks`, но
   полезно давать первой пробе отдельный запас).
4. **Прямой пробник сети перед массовым вердиктом** — у нас это частично есть
   («не наказывать, если не ответила ни одна цель пинга»); Throne доводит до явного
   глобального состояния `suspended`.
5. **«Прервано ≠ измерение»** — у нас появилось в 0.1.16 (`r.hard`), у них это
   `ErrTestAborted`.
6. **Идея групп по 10** — безопасна только как *эвристика по серверу* (`host:port`), а не по
   имени: одинаковый сервер = одинаковая судьба TCP-коннекта, но **не** одинаковая судьба
   скорости. Мы уже группируем по `host:port` в `FastPing` — расширять это на «соседние
   имена» рискованно: в сборниках подряд часто идут разные серверы одного провайдера с
   разными IP, и «все не работают» обычно означает «провайдер лёг», а не «соседи живы».

## 8. Шаг 3 в уточнённой формулировке: кластерная выборка (не отбраковка)

Ранее здесь было «групп по 10 нет и не надо» — это ответ на *отбраковку* по соседям.
Уточнённая идея автора другая и полезная: **сначала покрыть весь список выборкой**, затем
раскрывать только те места, где нашёлся рабочий конфиг, стримить найденное в пул и
повторять на сокращённом списке. Это не отбраковка, а планировщик.

Основание: в сборниках соседние строки действительно коррелируют, но не по номеру, а по
**инфраструктуре**. Пример:

```
hysteria2://<uuid>@185.151.243.186:443?sni=piodr-ru-74sel.my-fade.cloud...
hysteria2://<uuid>@<другой ip>:443?sni=<...>.my-fade.cloud...
```

Имя тут — эмодзи и флаги, а общее у соседей: протокол, порт, **домен провайдера**
(`my-fade.cloud`) и подсеть. Значит группировать надо по ключам из URL, а не по позиции.

Ключи (в порядке устойчивости):
1. **провайдер** — регистрируемый домен от `sni`/`host` (`my-fade.cloud`);
2. **линия** — `host:port` (уже используется в `FastPing`);
3. **схема+порт** — `hysteria2:443` (сборники часто склеены блоками по схеме);
4. запасной вариант для чистых IP — /24 (IPv4) и /48 (IPv6).

### Алгоритм

- **Фаза A — покрытие.** По одной линии на каждого провайдера (round-robin по кластерам, а
  не «каждая десятая строка»): дешёвый TCP-коннект. Итог: список провайдеров
  `alive / dead / unknown`. Стоимость — один проход `FastPing` (384 потока × 900 мс).
- **Фаза B — раскрытие.** Только у `alive`-провайдеров проверяются все их линии настоящим
  URL-тестом (батчами), результаты стримятся в пул; как только набралось N доказанно
  рабочих — подключение стартует, не дожидаясь остальных.
- **Фаза C — остаток.** `unknown`-провайдеры доезжают фоном; `dead` помечаются TTL’ом на
  кластер (6 ч), а не навсегда.

### Три списка вместо двух

| Список | Что хранит | Срок |
|---|---|---|
| `pool_*` | доказанно рабочие (пул текущей сети) | по замеру |
| `entries_*` (ЧС) | проверенные и отвергнутые | 7 дней (в плане — 1 ч для «провалов сети») |
| `candidates_*` (новый) | проверявшиеся, но не решённые: выборка, TCP-ок, URL-таймаут | до следующего прогона |
| `clusters_*` (новый) | вердикт провайдера: `alive/dead/unknown` + время | dead 6 ч, alive 24 ч |

Смысл `candidates_*`: следующий прогон не переделывает уже отсеянное и не путает «не
докачалось» с «мертво».

### Что это даёт и чего не даёт

- Даёт: время до первого рабочего конфига падает с «полный проход» до «проход выборки +
  один кластер». При 4000 строках и ~200 провайдерах это единицы секунд на покрытие и
  ~10–20 с до готового подключения.
- Даёт: провайдеры, которые легли, в следующий раз пропускаются целиком (TTL кластера).
- Не даёт: полноты. Одинокий живой сервер в мёртвом кластере выборка пропустит. Лечится
  тем, что непроверенное никогда не уходит в ЧС и фоновая фаза C всё равно доезжает.

Отличие от Throne: там тест идёт по всему списку партиями по 100 — надёжно, но до первого
рабочего можно ждать все партии. Кластерная выборка даёт выигрыш именно в
«время до подключения», а батч-ядро (раздел 7) — в «время до полного покрытия». Они
дополняют друг друга, поэтому и нужны вместе.

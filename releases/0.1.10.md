# 0.1.10 — проверки без Discord и YouTube, экран «Рабочие конфиги», починка ложных «нерабочих»

Три изменения. Первое — про то, **чем** проверяется канал, второе — исправление бага, из-за
которого рабочие конфиги выпадали из пула, третье — экран, где пул можно проверить и почистить
руками.

## Что нового

### Discord и YouTube убраны из тестовых целей

Раньше пинг и проверка канала шли в том числе на `discord.com` и `www.youtube.com`, а
проверка DPI-стратегий — на них же. Стало ясно, почему это плохо: публичные списки забиты
конфигами и стратегиями, которые открывают **ровно** Discord и YouTube (и ещё пару CDN) — и
ничего больше. По таким адресам нельзя судить, работает обход или нет: конфиг «проходит»
проверку, попадает в рабочие, а потом «VPN включён, а сайты не грузятся».

Что изменилось:

| Где | Было | Стало |
|---|---|---|
| `ping_targets` | `discord.com`, `www.instagram.com`, `x.com`, `www.facebook.com`, `www.youtube.com` | `www.instagram.com`, `x.com`, `www.facebook.com`, `www.linkedin.com`, `raw.githubusercontent.com` |
| `dpi_test_urls` | `discord.com`, `youtube/generate_204`, `instagram` | GitHub raw, `www.instagram.com`, `x.com` |
| `health_urls` | только `generate_204` (Cloudflare, Google, gstatic) | GitHub raw первым + прежние `generate_204` |
| Wi-Fi-набор, проверка канала | `discord`, `instagram`, `x`, `youtube`, Cloudflare | GitHub raw, `instagram`, `x`, `github.com`, Cloudflare |
| `speed_urls` | два файла с GitHub, затем два `generate_204` | GitHub raw (список конфигов) первым, второй файл с GitHub, `generate_204` — в конце |

`raw.githubusercontent.com` выбран не случайно: его нельзя «разрешить точечно» под один сервис,
в отличие от Discord или YouTube, — значит, скачанный через конфиг файл доказывает, что канал
годится для всего интернета.

DPI-стратегии, как и раньше, **не трогались**: обновились только цели проверок.

### Исправление: рабочие конфиги больше не помечаются неактивными

Причина найдена и подтверждена кодом. «Белый» конфиг, который пускает только Cloudflare и
Google, на запрос файла отвечает `204 No Content` — тела в ответе нет. Проверка считала это
провалом («серверы ответили 204 без тела — мерить нечего»), а провал — «жёстким», то есть
конфиг удалялся из пула и уходил в чёрный список на неделю. При этом туннель был полностью
рабочим: 204 как раз и доказывает, что канал есть.

Что сделано:

- пустой ответ `2xx/3xx` теперь считается **доказательством связности**: конфиг остаётся в
  пуле с минимальной скоростью и пометкой «скорость не измерена», в чёрный список не попадает;
- в короткой проверке (поиск, подключение — две попытки) последний слот теперь всегда отдаётся
  адресу `generate_204`, поэтому «белый» конфиг получает шанс ответить, а не проверяется двумя
  адресами GitHub, которые у него закрыты;
- подключение (`activate`) принимает такой конфиг и пишет «связность есть (скорость не
  измерена)» вместо «скорость не измерена ниже порога»;
- прерванная проверка (кнопка «Остановить») больше нигде не считается провалом конфига.

Тот же баг объясняет, почему часть конфигов, которые реально подключались, исчезала из пула
после первого же переподключения.

Записи, оставшиеся в чёрном списке от 0.1.9, живут неделю — то есть рабочие конфиги
оставались бы «неактивными» ещё долго после исправления. Поэтому при первом запуске 0.1.10
чёрный список очищается один раз: перепроверить десяток конфигов дешевле, чем неделю их не
видеть. Список рабочих конфигов (пул) не трогается.

### Экран «Рабочие конфиги»

Настройки → «Данные» → «Открыть рабочие конфиги», либо нажатие на карточку **ПУЛ** на главном
экране. Весь пул по скорости: КБ/с, пинг, когда мерили, схема, `host:port`, имя и стратегия
обхода. Для каждой строки:

- **Пинг** — только доступность сервера (TCP/TLS), быстро;
- **Перемерить** — поднимает отдельный экземпляр ядра и качает файл из `speed_urls` тем же
  порядком, что и подключение (сначала со «своей» стратегией, если она записана, иначе
  напрямую, затем одна попытка с общей стратегией); удачный замер обновляет запись пула;
- **Убрать** — из рабочих; **В ЧС** — из рабочих и в чёрный список на 7 дней.

Сверху — «Пропинговать все» и «Перемерить скорость у всех» (с подтверждением: это столько же
замеров, сколько конфигов). Внизу — **«В чёрный список все нерабочие (N)»**: активируется после
проверки и убирает из пула всё, что её не прошло. Порог скорости тот же, что в настройках,
поэтому «отвечает, но медленнее порога» тоже считается провалом; прерванная проверка — нет.

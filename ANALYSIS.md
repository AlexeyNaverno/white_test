# Разбор проекта «Обход Белых Списков» (v0.017)

> Документ описывает **предыдущую** версию 0.017 — ту, что анализировалась.
> Что из этого исправлено и вырезано в 0.0.1, см. в `README.md` (раздел «Что изменилось»).

Анализ по коду: 17 Java-файлов, 6 133 строки, 4 режима, 3 движка, 18 элементов управления.
Цель разбора — ответить на два вопроса: **почему подключается редко** и **что здесь лишнее**.

---

## 1. Что это на самом деле

Это не «аналог Throne/LXBox». Это **четыре разных приложения в одном APK**, между которыми
нет общего знаменателя, кроме VpnService:

| Слой | Где | Что делает |
|---|---|---|
| Транспорт | `BypassVpnService` + JNI `libbyedpi.so` (ciadpi + hev-socks5-tunnel внутри одного .so) | TUN → hev-socks5-tunnel → локальный SOCKS |
| Движок | `XrayEngine` (libv2ray), `TorEngine` (tor-android), ciadpi | поднимает локальный SOCKS: Xray — 10811, ciadpi — с 10910, Tor — 9050 |
| «Склад» | `ConfigRepository` + `assets/fallback/*` (2 300 конфигов, 732 КБ) | скачивание, дедуп, 4 уровня метрик, авто-обновление мостов и стратегий |
| «Мозг» | `MainActivity` (1 509 строк) + `SettingsActivity` | 3 разных алгоритма поиска, автогонка, авто-цепочка, фоновые докачки |

Схема пакета: `приложение → TUN (10.10.10.10/32, 0.0.0.0/0) → hev-socks5-tunnel → 127.0.0.1:SOCKS →
{Xray | ciadpi | Tor} → интернет`. Само приложение исключено из TUN
(`addDisallowedApplication`, `BypassVpnService:193`), поэтому движки работают «мимо» туннеля.

Технически это грамотно сделано (TUN, JNI, парсинг подписок, TLS-пинг, отмена задач).
Проблема не в качестве кода, а в **количестве слоёв, каждый из которых умеет нажать «нет»**.

## 2. Как происходит подключение — по шагам

`MainActivity.toggleConnection()` → `BypassVpnService.ACTION_START` → `startEngineSafely()`:

1. **Сразу поднимается TUN** с маршрутом `0.0.0.0/0` (`establishTun`, строки 176–197).
   С этой секунды весь трафик телефона уходит в пустоту, пока выбирается движок.
2. Для `vpn`: `buildVpnCandidates()` — до **8** конфигов: выбранный → «Вершина» → прошедшие
   тест → остальные (`MAX_VPN_CONNECT_ATTEMPTS`, строка 201).
3. Для каждого кандидата **сначала** пробуется «DPI-обход линии» (`startDesyncProxy`, вкл. по умолчанию),
   потом без него (`startXray`, строки 252–281).
4. Каждый кандидат проходит **гейт скорости**: скачать ≥ 512 КБ за ≤ 2000 мс
   (`speedGatePass`, строки 684–697). Не прошёл — конфиг считается мёртвым, берётся следующий.
5. Прошёл — `startTunnel(port)`, статус «on».
6. Далее монитор каждые 15 с, при 3 подряд неудачах — переключение (`startMonitor`, строка 749).

Для `dpi`: перебор до 12 стратегий, каждая — с гейтом «YouTube уложился в 2 с»
(`dpiGatePass`, строки 699–712).

Максимальное время до вердикта «ошибка» в режиме VPN:
`8 конфигов × (1.5 с desync + до 10 с ожидания SOCKS + до 3×2.5 с гейта) ≈ 5–6 минут`
**без интернета на телефоне**, потому что TUN уже поднят.

## 3. Почему подключается редко — 10 конкретных причин

### 3.1. Гейт «1 МБ за 2 секунды» — главная причина (P0)

`BypassVpnService.java:57-60, 684-697`

```java
private static final long GATE_MS = 2000;
private static final long GATE_MIN_BYTES = 512L * 1024L;
...
if (r.ok && r.ms <= GATE_MS && r.bytes >= GATE_MIN_BYTES) return true;
```

Это требование **устойчиво скачать 512 КБ за 2 с = 256 КБ/с ≈ 2 Мбит/с**, причём время
считается вместе с TLS-рукопожатием и по **бесплатному публичному** серверу, через телефон,
в варианте «через страну-выход». Любой рабочий, но медленный конфиг (а таких большинство)
**отбраковывается как мёртвый**. Throne/WireGuard-клиенты такого условия не ставят вообще —
поэтому «руками работает, здесь нет».

Это не проверка доступности, это фильтр по скорости, спрятанный под словом «проверка».

### 3.2. DPI-гейт проверяет не «открывается ли YouTube», а «успевает ли скачаться страница»

`BypassVpnService.java:699-712`

`downloadThroughSocks(url, ..., 3000, GATE_MAX_BYTES=1 МБ)` читает тело ответа, и требует
`r.ms <= 2000` на **всю** страницу youtube.com (~500–900 КБ). То есть DPI-стратегия должна
не просто «пробить ТСПУ», а отдать ~250–450 КБ/с. На мобильном интернете это часто не так —
стратегии, которые у пользователя в браузере работают, здесь падают 12 раз подряд и дают
«ни одна из 12 стратегий не пробила проверку YouTube».

### 3.3. Перебор DPI всегда один и тот же — «до победного» не существует

`BypassVpnService.java:538-552` + `rotateDpiStrategy()`

`DPI_MAX_ATTEMPTS = 12`, а `dpiStrategyList()` отдаёт файл `assets/strategies/byedpi_strategies.txt`
(111 строк) **в том же порядке**. Итог: 12 попыток — это всегда первые 11 строк файла
плюс сохранённая. «Ротация» меняет только первую в списке, остальные 11 те же.
111 стратегий, из которых 99 не будут опробованы никогда.

### 3.4. TUN поднимается до того, как найден рабочий движок

`startEngineSafely()` (строки 142–172): `establishTun()` → только потом поиск конфига.
5–6 минут «нет интернета» + системный диалог «приложение не отвечает» у пользователя.
Правильный порядок — сначала SOCKS, потом TUN (или TUN с `addRoute` только для нужного).

### 3.5. «DPI-обход линии до VPN» включён по умолчанию и ломает Reality

`Prefs.java:121` (`vpnDesync` = true), `BypassVpnService.java:252-275`, `XrayEngine:104-134`.

Идея: завернуть исходящее соединение Xray к VPN-серверу в локальный ciadpi. Для **Reality**
это плохая идея: Reality сверяет ClientHello с настоящим TLS целевого домена, а фрагментация/
disorder его меняет. В результате первая попытка каждого конфига идёт по заведомо испорченному
пути (плюс 1.5 с), и только потом — нормальная. Учитывая п.3.1, на «нормальную» попытку часто
уже не хватает времени/терпения.

### 3.6. Проверки удаляют конфиги — «самоочистка» превращается в самоуничтожение

`MainActivity.java:874` и `:978` (`ConfigRepository.deleteByHashes`).

После «Полной проверки» **физически удаляются** все конфиги, не прошедшие тест.
А тест — 3 параллельных инстанса Xray, ожидание SOCKS **2.5 с** (`waitSocksLocal(port, 2500)`,
строка 748) и чтение с таймаутом 1.5 с. На загруженном телефоне Xray стартует дольше 2.5 с —
и рабочий конфиг удаляется навсегда. Одна слабая сеть = вычищенный список.
Throne/LXBox ничего не удаляют — поэтому у них «всё работает».

### 3.7. Три инстанса Xray одновременно — «гонка топ-3»

`tryRaceTop3`, строки 286–345 + `MASS_CHECK_LANES = 3` в тестах.

Три ядра в одном процессе на телефоне: память, CPU, общий `initCoreEnv`. Библиотека
libv2ray рассчитана на один контроллер в процессе — по крайней мере это надо проверить
логами, потому что симптом «поднимаю 3, не отвечает ни один» ровно об этом.
Выигрыш от гонки при 5-секундной разнице в задержке между топ-3 — ноль.

### 3.8. Авто-режим: VPN → Tor → DPI

`engineFailed()`, строки 925–960. Под ТСПУ Tor без obfs4/webtunnel (а в APK их нет — сам
README это признаёт) не поднимется почти никогда, значит цепочка всегда тратит 150 секунд
(`TorEngine:150_000`) на заведомо провальный этап.

### 3.9. DNS: в режиме Tor UDP не работает вовсе

`establishTun` ставит DNS `1.1.1.1` (`Prefs.vpnDns`), трафик идёт в TUN → hev (`udp: udp`) →
Tor SOCKS5. **Tor не поддерживает UDP ASSOCIATE** → все DNS-запросы умирают. Туннель «on»,
приложения «нет интернета». Нужен отдельный DNS-канал (DoH/DoT через тот же SOCKS), а не
UDP 53 в туннель.

### 3.10. Мелочи, которые складываются

* IPv6 не маршрутизируется по умолчанию (`Prefs.ipv6 = false`) → часть сайтов идёт мимо
  туннеля, часть висит.
* `allocatePort()` при занятости всех 20 портов возвращает `base` — возможна коллизия портов.
* `switchToNextConfig()` берёт **первый попавшийся** живой конфиг, а не следующий по задержке
  (порядок `activeList()` = порядок скачивания).
* `updateLatencyAsync()` при каждом изменении статуса качает 256 КБ ради цифры в UI.
* `activeList()` парсит 2 300 конфигов и делает 2 300 чтений SharedPreferences на каждый вызов
  (вызывается в 4 местах, в том числе из сервиса при каждом подключении).

## 5. Что должно остаться (минимальная архитектура)

```
TUN (создаётся ПОСЛЕ готовности SOCKS)
  └─ hev-socks5-tunnel
       └─ SOCKS 127.0.0.1:1080
            ├─ Xray:  vless(reality/ws/grpc) · trojan · ss · vmess
            └─ ciadpi: 3–5 стратегий (не 111, не 12)
Конфиги: downloaded.txt + assets/fallback/start.txt (100 строк)
Поиск:   TCP/TLS-пинг → один реальный тест (Xray instance + HTTP 204 через SOCKS, таймаут 8 с)
         Ничего не удаляем. Результат — топ-5 по задержке.
Обновление: 1 кнопка, 2–3 источника, jsDelivr-зеркало, без фоновых докачек.
Tor: отдельный ручной режим «скачать список через Tor», без мостов масс-теста.
```

Ключевые правила, которых сейчас нет:

1. **Никогда не удалять конфиг по результату одного теста.** Только помечать «под вопросом».
2. **Не измерять скорость при подключении.** Достаточно `HTTP 204`/`generate_204` за 8 с.
3. **Один движок, одна попытка на конфиг, лимит 5 кандидатов.** Не 8 × 2 × гонка.
4. **TUN — последним шагом**, после того как SOCKS ответил.
5. **DNS — через SOCKS (DoH/DoT)**, а не UDP 53 в туннель.
6. Любая настройка либо влияет на работу, либо её нет (сейчас 2 из 20 — пустышки).

## 6. План работ

**P0 — вернуть работоспособность (не удаляя код)**
1. `GATE_MS`: 2000 → 8000; `GATE_MIN_BYTES`: 512 КБ → 16 КБ (или убрать гейт, оставить HTTP-код).
2. `dpiGatePass`: проверять только `ok` и код 200–399, без лимита времени на весь объём.
3. `waitSocksLocal`: 2500 → 8000 мс; `MASS_CHECK_LANES`: 3 → 1; `MAX_VPN_CONNECT_ATTEMPTS`: 8 → 5.
4. Выключить по умолчанию `VPN_DESYNC` и `VPN_RACE`.
5. Убрать `deleteByHashes` из обоих поисков (только помечать).
6. `establishTun()` вызывать после первого успешного SOCKS.

**P1 — удалить лишнее** (по таблице 4.1–4.3). Ожидаемый эффект: −3 700 строк, −700 КБ APK,
и главное — исчезают слои, которые могут отказать.

**P2 — довести до «одной кнопки»**: «Подключить» = поиск 5 лучших + подключение к первому,
всё остальное — в настройках за одним пунктом «Диагностика».

## 7. Оговорки

* Разбор статический: приложение не запускалось на устройстве, выводы — из кода и констант.
  Пункты 3.7 (три инстанса libv2ray) и 3.9 (UDP в Tor) стоит подтвердить логом, но оба
  следуют из архитектуры, а не из догадок.
* Отдельно стоит проверить `XrayEngine.buildConfigJson` на реальных ссылках из подписок:
  там молча теряются `type=http`, `plugin=obfs-local`, `packetEncoding`, `mux`; для `ss`
  принудительно ставится `security = "none"` (`XrayEngine:187`), то есть `ss+tls` не соберётся.
  Это ещё один класс «конфиг живой, а приложение его не умеет».
